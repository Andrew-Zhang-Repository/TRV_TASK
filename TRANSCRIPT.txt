Previously Fixed Bugs
Bug 1: apply_fill() — Sells Never Subtracted Position
Line 101


Code
Was (broken)
signed = qty if side == "B" else qty
Now (fixed)
signed = qty if side == "B" else -qty

What it did: Both branches were identical — buys and sells both added to the position. So if the taker bought 3 then sold 3, the position would show +6 instead of 0. This broke position tracking, PnL reporting, and the MAX_POS guard on line 74/76 (it would stop buying but never stop selling, since position never went negative).
Bug 2: Wrong NATS Subject for Order Entry
Line 85


Code
Was (broken)
await self.nc.request("ex.req", order.encode(), ...)
Now (fixed)
await self.nc.request(f"ex.req.{SENDER}", order.encode(), ...)

What it did: The protocol requires orders go to ex.req.<YOUR_SENDER> — the exchange uses the subject to verify the sender matches the message body. Sending to bare ex.req would have been rejected (or silently ignored) by the exchange.
Bug 3: Assumed Fill Size Instead of Parsing It
Line 96


Code
Was (broken)
filled = CLIP
Now (fixed)
filled = int(parts[2])

What it did: It assumed every accepted F order filled the full CLIP quantity. While F orders on v2.3+ are atomic (fill-in-full or reject), the reply Y <n> tells you the actual traded volume. The old code would mistrack position if the order was accepted with a different fill quantity than requested (e.g., Y 0 means accepted but nothing traded immediately for a limit order, though for F orders this is less likely). Parsing the actual value is the correct approach.

Remaining Issues / Things Still Worth Noting
1. Default Feed Mismatch — Line 27
python
FEED = os.environ.get("TAKER_FEED", "BTH6")
The default fallback is BTH6, but the exchange only lists AAH6, AAM6, AAU6 (see instruments.txt). If TAKER_FEED isn't set in the environment, the taker will try to trade a non-existent instrument and get reject code 202 (bad feedcode) on every order. This is fine in the Docker stack because docker-compose.yml sets TAKER_FEED: AAH6, but running the taker standalone without setting the env var would silently fail.
2. No Reconnection Logic — Line 122
python
nc = await nats.connect(NATS_URL)
If the NATS connection drops mid-session, the taker crashes. There's no reconnect callback, no retry, no error handler. The restart: on-failure in docker-compose partially mitigates this, but the taker would lose all position tracking state on restart (position resets to 0).
3. F-Order Y 0 Edge Case — Line 96–98
python
filled = int(parts[2])
self.apply_fill(side, filled, px)
self.fills += 1
If the exchange returns Y 0 (accepted, zero traded), the code calls apply_fill(side, 0, px) which does nothing harmful (adds 0 to position), but it increments self.fills anyway — cosmetically misleading. Not a functional bug, but not clean either.
4. Fill Price Assumption — Line 97
python
self.apply_fill(side, filled, px)
It uses px (the price it sent in the order) as the fill price. For a fill-and-kill crossing the spread, the actual fill price could differ (e.g., if there was price improvement). The truly correct approach would be to track fills from the market data E messages on ex.md.AAH6.PYTKR001, which report the exact execution price. This means the taker's PnL calculation is an approximation, not exact.
5. Broad Exception Swallowing — Line 86–87
python
except Exception:
   return  # timed out; treat as no fill
This catches all exceptions (not just TimeoutError), so any bug in the order-building code (e.g., px being None) would be silently swallowed. A more robust approach would catch nats.errors.TimeoutError specifically.

Bottom line: The three critical bugs from before are all fixed. What remains are minor robustness issues (default feed, reconnection, fill price assumption) — worth documenting in your NOTES.md as things you noticed and considered, but none of them will break the taker during a grading run where the env vars are properly set.
